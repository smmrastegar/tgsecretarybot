# ارتقای هفتگی (Weekly Upgrade)

> **ماشه:** وقتی مالک می‌گوید «ارتقای هفتگی بده» (یا «سیستم رو ارتقای هفتگی بده»)، همهٔ مراحل پایین به‌ترتیب اجرا می‌شود.
> همین فایل تنها مرجع است؛ مهارت `weekly-upgrade` (`.claude/skills/weekly-upgrade/SKILL.md`) فقط آن را باز می‌کند.
> بعد از هر اجرا، `docs/WEEKLY_LOG.md` به‌روز می‌شود.

هدف: هر هفته سیستم **سالم‌تر، سریع‌تر، قشنگ‌تر و کاربردی‌تر** شود، با تغییرهای کوچک و تأییدشده، نه بازنویسی.
این برنامه روی برنامهٔ روزانه (`docs/IMPROVEMENT_LOOP.md`) سوار است: همان نقشهٔ راه، همان متریک‌ها، همان دروازه‌های کیفیت.

اولویت‌ها به‌ترتیب (مالک تعیین کرده):
1. **سلامت API ساندکلاود و اسپاتیفای** (محدودیت‌ها، توکن‌ها، تغییرهای API) — مرحلهٔ ۱.
2. **UI/UX، مخصوصاً بخش موزیک و صفحهٔ کاربر** (پلیر و لینک‌ها/رمزهای کاربران) — مرحلهٔ ۳.
3. **ارتقای کارکرد** برای کاربر نهایی — مرحلهٔ ۴.
4. بهینه‌سازی و بهترین‌شیوه‌ها بر پایهٔ بنچمارک — مرحلهٔ ۵.

---

## مرحلهٔ ۰ — آماده‌سازی
- شاخهٔ `claude/telegram-secretary-bot-A0UsO`، آخرین `origin`، `npm ci` در صورت نیاز.
- MCP: `deploy_status` (سرویس‌ها فعال؟ `sha` = `behindRemote`؟)، `roadmap_list`.
- یک آیتم نقشهٔ راه «ارتقای هفتگی — <تاریخ جمعه>» با `kind: improvement`، `source: weekly` ثبت کن و `in_progress` کن (پایان هفته `done` با `outcome`).

## مرحلهٔ ۱ — سلامت API‌ها (ساندکلاود و اسپاتیفای) ⭐ اولویت اول
هدف: محدودیت نخوردن، و اگر خورد زود فهمیدن.

متریک‌ها (از قبل جمع می‌شوند، `lib/api-health.ts` و جدول `api_health_daily`):
- هر درخواست به API: موفق / «محدود شدی» (۴۲۹) / خطا، به تفکیک روز؛ آخرین زمان و مدت محدودیت.
- آزمایش فعال هر ۶ ساعت (توکن برنامه + یک جستجو/resolve)؛ تغییر وضعیت در لاگ سیستم (`source: music`) و گزارش شبانه (بخش «🎧 موزیک و APIها»).
- در داشبورد: **موزیک ← سلامت اسپاتیفای و ساندکلاود** (دکمهٔ «آزمایش همین الان»).

چک‌لیست هفتگی:
1. `SELECT * FROM api_health_daily WHERE day >= CURRENT_DATE - 7 ORDER BY day DESC, provider` — هر `limited > 0` یا روند خطای بالا = علت‌یابی (کدام مسیر کد زیادی درخواست زد؟).
2. تنظیمات: `scMetaPauseUntil` (توقف اصلاح نام)، `apiProbe_spotify`، `apiProbe_soundcloud`، `apiProbeAt`، `scWatchAt` (آخرین بررسی لایک‌های ساندکلاود).
3. ساندکلاود: توکن حساب‌ها تازه می‌شود؟ (`music_tracks` ساندکلاود با `status='failed'`)، دانلودها سالم؟ `scWatchStep` لایک تازه آورده؟ حساب‌ها هنوز وصل‌اند؟
4. اسپاتیفای: جستجوی کاتالوگ جواب می‌دهد؟ حساب‌های کاربری (`spotify_accounts`) توکن معتبر دارند؟ آهنگ‌های `failed` چندتاست؟
5. **بودجهٔ درخواست (قانون):** هیچ حلقه‌ای بدون فاصله (≥۴۰۰ms برای کاتالوگ، ≥۱۲۰۰ms برای پاک‌سازی انبوه) و بدون توقف روی ۴۲۹ نباید به این دو API بزند. هر قابلیت تازه‌ای که به این API‌ها می‌زند باید: کش داشته باشد، دسته‌ای نباشد، و `SpotifyRateLimited` / `ScRateLimited` را بگیرد و **بایستد**.
6. تغییرهای API را بررسی کن (مستندات رسمی: developer.spotify.com/documentation/web-api و developers.soundcloud.com/docs/api) — اعلان‌های تازه دربارهٔ سهمیه، حذف endpoint، یا شرط‌های حالت توسعه.
7. اگر محدودیت طولانی خورد: **تکرار نکن**؛ زمان پایانش را ثبت و به مالک گزارش بده؛ تا آن موقع فقط کارهای بدون API (UI، بهینه‌سازی) را پیش ببر.
8. توصیه‌های امنیتی: توکن/ClientSecret که در چت دیده شده باید چرخانده شود (آیتم‌های نقشهٔ راه)، و هرگز در ریپو/لاگ نیاید.

## مرحلهٔ ۲ — اندازه‌گیری کلی سیستم
- `metrics_snapshot` (+`backfill_days=7`) و `metrics_daily` (days=14): هفتهٔ جاری در برابر هفتهٔ قبل. کاندیدها: هر شاخص با روند ⚠️.
- `feature_usage`: قابلیت خوابیده (dormant/empty) → پیشنهاد (راه‌اندازی/تعمیر/حذف) در گزارش.
- `SELECT source, count(*) FROM system_errors WHERE created_at > NOW() - INTERVAL '7 days' GROUP BY 1 ORDER BY 2 DESC` — خطای تکراری = آیتم `fix`.
- `npm run audit:routes` (مسیر عمومی بدون گارد = خطای قرمز)، `npm audit --omit=dev`، `npm outdated`.
- موزیک: آهنگ‌های ناموفق، صف اصلاح نام ساندکلاود (`meta_state='review'`)، فایل‌های مشکوک (`music_verify`)، گزارش‌های پلیر (`music_reports`)، کرش‌های کلاینت (`system_errors` با `source='client'`).
- بنچمارک پلیر: `scripts/player-bench.mjs` روی بیلد production → سطر تازه در `docs/PLAYER_BENCH_LOG.md`؛ هر شاخصی که بدتر شده = آیتم.

## مرحلهٔ ۳ — ممیزی UI/UX (موزیک اول)
روش (Playwright با mockهای هم‌شکل API؛ الگو: `scripts/player-bench.mjs`، و اصول `docs/UI_PRINCIPLES.md`):
- عرض‌های ۳۲۰ / ۳۶۰ / ۳۹۰ / ۴۱۲ / ۷۶۸ / ۱۲۸۰؛ اسکرین‌شات + اندازه‌گیری: سرریز افقی (`scrollWidth === clientWidth`)، کنترل‌های زیر ۴۰–۴۴px، متن زیر ۱۲px، کنتراست، فوکوس صفحه‌کلید، برچسب `aria`.
- **صفحه‌های کاربر:** پلیر (خانه، جستجو، کتابخانه، تمام‌صفحه، صف، منوها)، ورود با لینک/رمز عددی، تنظیمات پلیر، آفلاین/خطا/خالی.
- **داشبورد موزیک:** بخش‌ها (اسپاتیفای، ساندکلاود، سلامت API، لینک‌ها و رمزها، آمار).
- وضعیت‌های بارگذاری/خالی/خطا/آفلاین برای هر صفحه؛ `confirm()/prompt()` بومی ممنوع (به `components/ui/Dialogs.tsx` برو).
- مقایسه با چک‌لیست `docs/PLAYER_BENCHMARK.md` (Spotify / Apple Music / YouTube Music / Tidal / Plexamp): هر ردیف ❌/🟡 یک کاندید.
- خروجی: حداکثر ۳ مشکل بیشترین اثر → پیاده‌سازی در همین هفته؛ بقیه آیتم نقشهٔ راه.

## مرحلهٔ ۴ — ارتقای کارکرد (سمت کاربر اول)
- فهرست کاندیدها را از این منابع بساز: ردیف‌های ❌/🟡 بنچمارک، `roadmap_list`، گزارش‌های کاربران پلیر، `music_events` (چه چیزی بیشتر استفاده می‌شود/اسکیپ می‌شود)، درخواست‌های اخیر مالک.
- معیار انتخاب: اثر برای کاربر ÷ هزینه؛ بدون خطر برای APIها؛ قابل‌ تحویل در همین هفته.
- مثال‌ها: ارتقای جستجو، صف و پخش بعدی، اشتراک‌گذاری، آفلاین، لینک‌ها/رمزها و دسترسی‌های کاربران، هوشمندسازی پلی‌لیست، اتصال‌های اسپاتیفای/ساندکلاود، ویرایش نام آهنگ.
- هر قابلیت = آیتم نقشهٔ راه (`kind: feature|improvement`)، تست واحد برای منطق خالص، متن فارسی در داشبورد، انگلیسی در پلیر.

## مرحلهٔ ۵ — بهینه‌سازی و بهترین‌شیوه‌ها
- **سرعت:** اندازهٔ JS هر مسیر (خروجی `next build`)، `PLAYER_BENCH_LOG`، اندازهٔ پاسخ `/api/music` (هر آهنگ یک ردیف؛ اگر از ~۱ MB گذشت: صفحه‌بندی/فشرده‌سازی)، کش و `Cache-Control`، سرویس‌ورکر.
- **دیتابیس:** کوئری‌های کند (`EXPLAIN ANALYZE` روی مسیرهای داغ موزیک و پیام‌ها)، ایندکس‌های ازدست‌رفته، حجم جدول‌های لاگ (پاک‌سازی/آرشیو).
- **پایداری:** بازخوانی با تلاش مجدد/جلوگیری از ۴۲۹ (الگوی `catalogGet`: فاصله + توقف)، تایم‌اوت‌ها، خطاهای تکراری در `system_errors`.
- **امنیت:** `audit:routes`، `npm audit`، چرخش رمزهای دیده‌شده.
- **بنچمارک:** تازه‌ترین رفتار برنامه‌های مرجع را بخوان (Spotify، Apple Music، YouTube Music، Plexamp) و فقط چیزی را بیاور که با معماری فعلی می‌خواند.

## مرحلهٔ ۶ — اجرا (حداکثر ۳ تا ۵ تغییر کوچک)
دروازه‌ها، دقیقاً مثل برنامهٔ روزانه: `npm run typecheck && npm run lint -- --max-warnings=0 && npm test && npm run build` (**هر چهار**) ← commit ← push ← `deploy_now` ← صبر تا `deploy OK → <sha>` در `deploy_status` ← تأیید رفتار واقعی (کوئری/لاگ/اسکرین‌شات) ← در صورت خرابی همان لحظه revert.
> خطای lint بیلد را می‌شکند و دیپلوی را متوقف می‌کند (قبلاً رخ داد): پیش از push حتماً `npx next lint` را اجرا کن.

## مرحلهٔ ۷ — ثبت و گزارش
- `roadmap_update` هر آیتم (`done` + `commit_sha` + `outcome` یک جملهٔ فارسی)، و آیتم‌های کشف‌شده را با `roadmap_add` (`source: weekly`) بگذار؛ آیتم جمعهٔ بعد را `planned` کن.
- سطر هفته را به `docs/WEEKLY_LOG.md` اضافه کن: تاریخ، شاخص‌های کلیدی (امتیاز پایداری، خطاها، دقیقهٔ پخش، وضعیت API‌ها)، تغییرها (sha)، یافته‌های بازِ مانده.
- `send_rich_message` به مالک (chat `63530821`): عنوان «🚀 ارتقای هفتگی — <تاریخ>»، ≤۱۵ خط: چه شد، شاخص‌ها، وضعیت API‌ها، تصمیم/خطرِ نیازمند مالک.

## خطوط قرمز
- به **مانیتورینگ اینستاگرام** دست نزن (تصمیم مالک).
- هرگز توکن/کلید در ریپو، لاگ، پیام یا کامیت نیاید.
- درخواست انبوه یا بدون فاصله به اسپاتیفای/ساندکلاود ممنوع (هزینهٔ آن ۲۳ ساعت قطع بود).
- تغییر مخرب اسکیمای دیتابیس، بازنویسی بزرگ، یا ارتقای وابستگی عمده فقط با تأیید مالک.
- هر هفته حداکثر ۳ تا ۵ تغییر؛ کوچک و تأییدشده بهتر از بزرگ و ناتمام است.
