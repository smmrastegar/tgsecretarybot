# برنامه‌ی بهبود روزانه (Continuous Improvement Loop)

هدف: سیستم هر روز کمی بهتر، پایدارتر و پرکارتر از دیروز باشد؛ تدریجی ولی
**روزانه و با برنامه**. سه جزء دارد: اندازه‌گیری، دستور کار، چرخه‌ی اجرا.

## ۱. اندازه‌گیری — `system_metrics_daily`

هر شب ۰۰:۲۰ به وقت تهران، کران `/api/cron/metrics-daily` روزِ تمام‌شده را
از روی جدول‌های محصول می‌شمارد (`lib/metrics.ts`) و یک ردیف JSON ذخیره
می‌کند. هیچ عددی تخمینی نیست؛ همه شمارش همان روز است.

| بخش | چه چیزی |
|---|---|
| کارکرد (`work`) | پیام‌های پردازش‌شده، هشدار فوری، پاسخ خودکار، پیاده‌سازی صدا، مدیای آرشیوشده، تطبیق/فوروارد قوانین، خلاصه‌ی گفتگو و گروه، ایمیل، پیامک، کارهای استخراج‌شده، برد تسک، واچ‌لیست، مانیتورینگ، یادآور پیگیری، … |
| پایداری (`reliability`) | خطا/هشدار سیستم، دیپلوی موفق/ناموفق، خطای مسیریابی مدیا، ۵ منبع خطای اول |
| هزینه (`cost`) | فراخوانی/توکن/دلار AI، دلار HikerAPI |
| بهبود (`improvement`) | آیتم‌های نقشه‌ی راه که آن روز بسته شد، تعداد آیتم باز |
| مشتق (`derived`) | نرخ موفقیت فوروارد، خطا به ازای ۱۰۰ پیام، هزینه‌ی AI به ازای پیام، **امتیاز پایداری ۰–۱۰۰** |

امتیاز پایداری عمداً ساده و قابل توضیح است: از ۱۰۰ شروع، هر خطا ۲− (سقف ۴۰)،
هر فوروارد ناموفق ۵− (سقف ۲۰)، هر خطای مسیریابی ۲− (سقف ۱۰)، دیپلوی ناموفق ۲۰−.

گزارش شبانه (Rich Message به مالک) هر شاخص را کنار **میانگین ۷ روز قبل** با
فلش روند نشان می‌دهد (⚠️ یعنی روند در جهت بد). در پنل: **تنظیمات ← نقشه‌ی راه
و بهره‌وری** (`/roadmap`) جدول ۱۴ روز اخیر را دارد.

MCP: `metrics_snapshot` (محاسبه/ذخیره، `send=true` برای ارسال گزارش،
`backfill_days=N`)، `metrics_daily` (خواندن اسنپ‌شات‌ها).

## ۲. دستور کار — `improvement_items` (نقشه‌ی راه)

هر فیچر جدید، رفع باگ یا بهبود فیچر قبلی یک آیتم است:
`kind` (feature / fix / improvement / chore)، `priority` (۱ بالا … ۳ پایین)،
`status` (idea → planned → in_progress → done | dropped)، `planned_for`
(روزی که باید انجام شود)، `commit_sha` و `outcome` وقتی بسته شد.

- پنل: `/roadmap` — افزودن، تغییر وضعیت/اولویت/تاریخ، ویرایش، حذف.
- MCP: `roadmap_list`, `roadmap_add`, `roadmap_update`.
- گزارش شبانه: «دیروز تحویل شد» + «برنامه‌ی امروز» از همین جدول.

قاعده: **هر روز دست‌کم یک آیتم `planned` داشته باشد.** اگر نباشد، گزارش هشدار
می‌دهد.

## ۳. چرخه‌ی روزانه

اجرای خودکار: یک Routine روزانه در Claude Code (۰۶:۰۰ تهران) همین چرخه را
می‌گرداند — راه‌اندازی و متن پرامپت در `docs/DAILY_ROUTINE_PROMPT.md`.

```
اندازه‌گیری (شب)  →  انتخاب (صبح)  →  اجرا  →  گیت  →  دیپلوی  →  تأیید  →  ثبت
```

1. **اندازه‌گیری**: اسنپ‌شات شب قبل + گزارش. خطاهای تازه در `system_errors`
   و شاخص‌های با روند ⚠️ کاندیدای آیتم `fix` هستند (منبع: `metrics` / `errors`).
2. **انتخاب**: یک آیتم `planned` امروز (یا بالاترین اولویت باز). کوچک و
   قابل تحویل در یک روز. `status = in_progress`.
3. **اجرا**: شاخه‌ی `claude/telegram-secretary-bot-A0UsO`، تست واحد برای منطق
   خالص، تغییر اسکیمای DB فقط از `lib/db/migrations.ts`.
4. **گیت**: `npm run typecheck && npm run lint -- --max-warnings=0 && npm test && npm run build`.
   CI روی GitHub همین را می‌زند؛ `auto-deploy.sh` هم قبل از ری‌استارت تست می‌گیرد.
5. **دیپلوی**: push → تایمر ۳۰ ثانیه‌ای، یا MCP `deploy_now`؛ با `deploy_status`
   تا `deploy OK → <sha>` صبر کن.
6. **تأیید**: رفتار واقعی را چک کن (پیام تست، کوئری DB، `system_errors`).
   اگر خراب شد: revert در همان روز، نه فردا.
7. **ثبت**: `roadmap_update {status: done, commit_sha, outcome}`. آیتم‌های
   کشف‌شده‌ی جدید را با `roadmap_add` (source: agent) ثبت کن، نه این که
   همان روز انجام دهی.

### خطوط قرمز
- مانیتورینگ اینستاگرام را دستی تغییر نده (تصمیم مالک).
- توکن‌ها و کلیدها هرگز داخل ریپو، لاگ، یا پیام.
- تغییر بزرگ (بازنویسی، تغییر اسکیمای مخرب) بدون آیتم تأییدشده‌ی مالک انجام نمی‌شود.
- هر روز حداکثر یکی دو تغییر کوچک؛ «تدریجی ولی هر روز».
